Entity-Relationship Diagrams (ERD)

An Entity-Relationship Diagram is a visual model of a database. It shows the entities we need to store, their attributes, and the relationships and cardinality between them. In exam questions you may need to draw, complete, read or correct an ERD.

Conceptual Anchor

The Database Blueprint

An ERD is like a blueprint drawn before construction. It does not contain every database record. Instead, it shows what kinds of things must be stored and how those things are connected. A good ERD lets a developer check the structure before creating database tables.

Core ERD Concepts

ConceptMeaningExample
EntityA person, object, place or concept about which data is storedSTUDENT, COURSE, TEACHER
AttributeA property that describes an entityStudentID, Name, Email
RelationshipAn association between entitiesSTUDENT enrols on COURSE
CardinalityHow many instances of one entity can relate to another1:1, 1:M, M:M
Identifier / PKAn attribute used to uniquely identify an entity instanceStudentID

Crow’s Foot Notation

Read the pair, not one symbol

At each end of a relationship, the symbols work together: one mark gives the minimum participation and the other gives the maximum. For example, O< means zero or many.

Extension: other ERD notations

Chen notation uses rectangles for entities, ovals for attributes and diamonds for relationships. This lesson uses Crow’s Foot consistently because it maps naturally to relational table design and is common in database tools.

Read Cardinality in Both Directions

Exam technique

Before drawing symbols, write two sentences: “One A can have how many B?” and “One B can have how many A?” This prevents many cardinality errors.

Choose the correct cardinality.

How to Build an ERD

1 Read the scenario

Underline important nouns and verbs. Nouns often suggest entities; verbs often suggest relationships.

2 Identify entities

Choose the major things that need their own stored records. Do not turn every word into an entity.

3 Add attributes and identifiers

Add important properties and a suitable primary key / identifier to each entity.

4 Draw relationships

Connect entities using the relationship described by the scenario.

5 Determine cardinality

Read every relationship in both directions, then add the Crow’s Foot symbols.

6 Review the diagram

Check entities, attributes, relationship lines, cardinality, optionality where stated, and whether an M:M relationship needs resolving for relational implementation.

Many-to-Many Relationships

Conceptual vs relational design

A conceptual ERD may show an M:M relationship directly. When implementing it as relational tables, it is normally resolved with an associative (junction) entity.

Visual Exam Practice

Q1: The diagram shows MEMBER and LOAN. One member may make zero or many loans; every loan belongs to exactly one member. Complete the missing cardinality near LOAN. [2]

Reveal marking points
Circle / optional minimum near LOAN [1] Crow’s Foot / many maximum near LOAN [1]

Q2: An exam diagram shows CUSTOMER 1:1 ORDER. The scenario says one customer may place many orders and every order belongs to one customer. State the error and correct the relationship. [2]

Reveal marking points
The shown cardinality is incorrect [1] Correct relationship is 1:M from CUSTOMER to ORDER (or equivalent Crow’s Foot notation) [1]

Q3: A diagram shows STUDENT M:M COURSE. Add the entity needed for relational implementation and state one attribute that belongs there. [2]

Reveal marking points
Add an associative entity such as ENROLMENT [1] Suitable relationship attribute, e.g. Grade / EnrolmentDate [1]

Common Pitfalls

Reading only one direction

Always read a relationship both ways. The statement about one side does not automatically tell you the full cardinality.

Turning every noun into an entity

Name, Email and DateOfBirth are usually attributes, not separate entities.

Mixing ERD notations

Do not use Crow's Foot on one relationship and Chen diamonds/ovals elsewhere in the same diagram unless the task explicitly asks for a different notation.

Treating M:M as impossible

M:M is valid in a conceptual ERD. It normally needs an associative entity when converted into relational tables.

Adding optionality that the scenario never states

If the question only asks for basic 1:1, 1:M or M:M cardinality, do not invent zero/optional participation unless the wording supports it.

Exam Practice

Q1: A medical centre stores doctors and appointments. Each doctor can have many appointments. Each appointment is assigned to exactly one doctor. Draw an ERD showing both entities, suitable attributes and cardinality. [5]

Reveal marking points
DOCTOR entity [1] APPOINTMENT entity [1] Suitable identifier/attributes shown [1] Relationship shown [1] Correct 1:M cardinality from DOCTOR to APPOINTMENT [1]

Q2: A student can join many clubs and each club can contain many students. State the conceptual cardinality and explain how it would normally be implemented in a relational database. [3]

Reveal marking points
M:M relationship [1] Create an associative/junction entity such as MEMBERSHIP [1] This produces two 1:M relationships / stores the links between student and club [1]

Q3: A partially completed ERD shows LIBRARY_MEMBER and LOAN but no symbols at the LOAN end. The scenario states that a member may have no loans or many loans. Draw the missing symbols. [2]

Reveal marking points
Optional / zero symbol [1] Many / Crow’s Foot symbol [1]

Q4: Explain why Name is usually an attribute of STUDENT rather than a separate entity. [2]

Reveal marking points
Name is a property that describes a student [1] It does not normally require its own independent records/relationships [1]
