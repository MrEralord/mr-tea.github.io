Entity-Relationship Diagrams (ERD)

An Entity-Relationship Diagram is a visual model used in database design. It shows entities, their attributes, the relationships between them and the cardinality of those relationships. Exam questions may ask you to draw, complete, read or correct an ERD.

Conceptual Anchor

The Database Blueprint

An ERD is a blueprint of database structure. It shows what kinds of things are stored and how those things are connected before the final database tables are implemented.

Conceptual ERD Notation

The classroom material first introduces ERD using a conceptual notation: entities are rectangles, attributes are ovals, relationships are diamonds, and cardinality may be shown with labels such as 1, N or M.

Why this matters

If an exam question gives you a diagram using diamonds and ovals, continue using that notation consistently. Do not suddenly switch to a table-style Crow’s Foot diagram halfway through the answer.

Cardinality

Cardinality describes how many occurrences of one entity can be associated with occurrences of another entity. Always read the relationship in both directions.

RelationshipMeaningExample
1 : 1One occurrence relates to one occurrencePerson — Insurance Number
1 : NOne occurrence relates to many occurrencesCompany — Employee
N : 1Many occurrences relate to one occurrenceStudents — Class
M : NMany occurrences relate to many occurrencesOrder — Item

Exam habit

Write two sentences before drawing the connection: “One A can have how many B?” and “One B can have how many A?”.

Choose the correct cardinality.

Compact / Table-Style ERD

Later, the same model can be shown more compactly by placing the attributes inside each entity box. In this form, cardinality is often shown with line-ending symbols such as one, many, zero-or-one, one-or-many and zero-or-many.

Conceptual notation ≠ compact notation

They describe the same database ideas, but the shapes are different. Use the notation shown in the question or the notation requested by the teacher/exam.

How to Build an ERD

1 Read the scenario

Identify the important nouns and verbs.

2 Identify entities

Choose the main things that require their own stored records.

3 Add attributes

Add the properties that describe each entity and identify suitable primary keys.

4 Add relationships

Connect related entities. In conceptual notation, represent the relationship consistently with the diagram style.

5 Determine cardinality

Read each relationship in both directions and add 1/N/M or the required line-ending symbols.

6 Review

Check entities, attributes, relationships, cardinality and whether an M:N relationship requires a junction table for relational implementation.

Resolving a Many-to-Many Relationship

A many-to-many relationship can be valid in a conceptual ERD. When implementing it as a relational database, introduce a junction table to convert the relationship into two one-to-many relationships.

Key link

The junction table normally contains foreign keys referencing the primary keys of the two related tables. Those foreign keys may also form a composite key.

Q1: One CUSTOMER can place many ORDERS. Each ORDER belongs to one CUSTOMER. Add the missing cardinality near ORDER. [1]

Reveal marking point
N / many [1]

Q2: Redraw the same CUSTOMER—ORDER relationship using the compact/table-style notation. [2]

Reveal marking points
One side shown at CUSTOMER [1] Many side shown at ORDER [1]

Q3: A conceptual ERD shows STUDENT M:N COURSE. Explain what must be added when the model is implemented as relational tables. [2]

Reveal marking points
Add a junction/associative table such as ENROLMENT [1] Use foreign keys to link STUDENT and COURSE / produce two 1:N relationships [1]

Common Pitfalls

Using the wrong connection scheme

If the question gives 1/N labels and diamonds, continue with that style. If it gives compact entities with line-ending symbols, continue with that style.

Reading only one direction

Always check both directions before deciding whether the relationship is 1:1, 1:N or M:N.

Attribute used as an entity

Name, Email and DateOfBirth usually describe an entity rather than becoming separate entities themselves.

Leaving M:N unresolved in relational implementation

Add a junction table when converting a many-to-many conceptual relationship into relational tables.
