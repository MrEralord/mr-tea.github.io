Entity-Relationship Diagrams (ERD)

An Entity-Relationship Diagram is a visual model of a database. It shows the entities we need to store, their important attributes, and the relationships and cardinality between them.

Conceptual Anchor

The Database Blueprint

An ERD is like a blueprint drawn before construction. It does not contain every database record. Instead, it shows what kinds of things must be stored and how those things are connected. A good ERD lets a developer check the structure before creating database tables.

Core ERD Concepts

ConceptMeaningExample
EntityA person, object, place or concept about which data is storedSTUDENT, COURSE, TEACHER
AttributeA property that describes an entityStudentID, Name, Email
RelationshipAn association between entitiesSTUDENT enrols on COURSE
CardinalityHow many instances of one entity can relate to another1:1, 1:M, M:M
Identifier / PKAn attribute used to uniquely identify an entity instanceStudentID

1 Read a simple ERD

STUDENT ---------------- StudentID Name Email 1 ─────────< M COURSE ---------------- CourseID CourseName

The diagram says that one side is related to many on the other side. On this page, text diagrams use a simplified Crow's Foot style: | means one and < means many.

One notation for this lesson

This lesson uses Crow's Foot as the main ERD notation. Some textbooks use Chen notation with ovals and diamonds; that is another valid notation, but mixing both in one diagram makes the model harder to read.

How to Build an ERD

1 Read the scenario

Underline important nouns and verbs. Nouns often suggest entities; verbs often suggest relationships.

2 Identify entities

Choose the major things that need their own stored records. Do not turn every word into an entity.

3 Add attributes

Add important properties and a suitable identifier to each entity.

4 Identify relationships

Ask how one entity is associated with another: teaches, owns, contains, enrols on, books, borrows.

5 Determine cardinality

Ask both directions: “How many B can one A have?” and “How many A can one B have?”

6 Review the diagram

Check that every entity is necessary, relationships match the scenario, cardinalities are logical, and M:M relationships are handled appropriately when the model is implemented relationally.

Example scenario

A school stores students and clubs. Each student can join several clubs. Each club can contain many students.

Step 1 — entities: STUDENT, CLUB Step 2 — relationship: STUDENT joins CLUB Step 3 — cardinality: STUDENT M : M CLUB

Many-to-Many Relationships

Conceptual vs relational design

A conceptual ERD can show an M:M relationship directly. When implementing that relationship in a relational database, it is normally resolved with an associative (junction) entity.

Before implementation

STUDENT M ───────── M COURSE

After resolving M:M

STUDENT 1 ────< ENROLMENT >──── 1 COURSE STUDENT StudentID Name ENROLMENT StudentID CourseID Grade COURSE CourseID CourseName

The associative entity ENROLMENT stores facts about the relationship itself, such as Grade.

Common Pitfalls

Guessing cardinality from one direction

Always ask the relationship in both directions. “One customer can make many orders” is incomplete until you also confirm whether one order belongs to one or many customers.

Turning every noun into an entity

Name, Email and DateOfBirth are usually attributes, not separate entities.

Mixing ERD notations

Do not use Crow's Foot on one relationship and Chen diamonds/ovals elsewhere in the same diagram unless the task explicitly asks for a different notation.

Treating M:M as impossible

M:M is valid in a conceptual ERD. It normally needs an associative entity when converted into relational tables.

Extension: other ERD notations

Chen notation commonly uses rectangles for entities, ovals for attributes and diamonds for relationships. It is valid, but this lesson uses Crow's Foot consistently because it maps naturally to relational table design.
