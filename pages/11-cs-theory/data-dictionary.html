Data Dictionary

A data dictionary documents the structure and rules of data in a database. It stores metadata — information such as an attribute's name, data type, meaning, size and constraints.

Conceptual Anchor

The Blueprint Analogy

A building contains real rooms, doors and furniture, while a blueprint describes how the building is structured. In the same way, a database table stores real values, while a data dictionary describes what those values mean and the rules used to store them.

1 Data vs Metadata

Actual table data S001 · Dana · 2009-11-03 · dana@nis.edu.kz
Described by metadata StudentID · VARCHAR(4) · required · format S999
Data Dictionary Meaning, type, size and rules for each attribute

Database table = values. Data dictionary = description of those values and their rules.

Why Use a Data Dictionary?

Document the design

Makes the meaning, type and expected structure of each attribute clear.

Keep data consistent

Agreed types, sizes and constraints reduce inconsistent definitions.

Support implementation & maintenance

Developers can create, validate and maintain tables without guessing what each attribute was intended to store.

A new developer sees an attribute called Status, but does not know whether it stores Active/Inactive, Paid/Unpaid or something else. What should the data dictionary provide?

Anatomy of a Data Dictionary Row

The exact columns used in a data dictionary vary between organisations and database systems. On this page we use a compact SQL-style format that makes the link to database implementation clear.

SQL-style data types

This lesson uses familiar SQL-style names such as VARCHAR(50), INT, DATE, DECIMAL(8,2) and BOOLEAN. Exact type names can differ between database management systems.

Dictionary item What it tells us Example
Attribute Name of the field / column Email
SQL Data Type Kind of value and, where relevant, maximum size / precision VARCHAR(100)
Description Clear meaning of the attribute Student school email address
Constraints / Validation Important rules or restrictions Optional; must use school email domain
Example One valid sample value dana@nis.edu.kz

One Complete Example: STUDENTS

Attribute SQL Data Type Description Constraints / Validation Example
StudentID VARCHAR(4) Unique student identifier Required; format S999 S001
Name VARCHAR(50) Student full name Required; must not be empty Dana Kim
BirthDate DATE Student date of birth Required; valid calendar date 2009-11-03
Email VARCHAR(100) Student school email address Optional; school email format dana@nis.edu.kz

Identifier ≠ number

StudentID contains digits, but it is still stored as VARCHAR(4) because values such as S001 are identifiers, not numbers used for arithmetic.

Extension: Dictionary → SQL Table

A data dictionary can guide the implementation of a database table. The dictionary is documentation; SQL is the implementation.

Dictionary decision Possible SQL implementation
StudentID | VARCHAR(4) | Required StudentID VARCHAR(4) NOT NULL
Name | VARCHAR(50) | Required Name VARCHAR(50) NOT NULL
BirthDate | DATE | Required BirthDate DATE NOT NULL
Email | VARCHAR(100) | Optional Email VARCHAR(100)
CREATE TABLE Student ( StudentID VARCHAR(4) NOT NULL, Name VARCHAR(50) NOT NULL, BirthDate DATE NOT NULL, Email VARCHAR(100) );

Important

The SQL shown here is an implementation example, not a replacement for the data dictionary. The dictionary also explains meaning, examples and validation rules that may not all appear directly in a short CREATE TABLE statement.

Common Pitfalls

Data ≠ metadata

Dana Kim is data. “Name is VARCHAR(50) and required” is metadata.

Codes are not automatically numeric

An identifier such as S001 should not be stored as INT just because it contains digits.

Vague descriptions

“Email data” or “birth data” is too vague. Describe exactly what the attribute represents.

Missing constraints

If a requirement says a value is required, optional, limited to a range or must follow a format, record that rule.

SQL type names can vary

Different DBMS products may use slightly different type names or features. The important skill is choosing a type that matches the meaning of the data.

Exam Practice

Q1: Explain the purpose of a data dictionary. [3]

Reveal marking points
Documents metadata about the database structure. [1] Describes attributes such as data type, size/format, meaning or constraints. [1] Supports consistent implementation, validation, maintenance or communication between developers. [1]

Q2: A school requires an optional email address with a maximum length of 100 characters. Create a suitable data-dictionary row for Email. [4]

Reveal marking points
Attribute: Email [1] Suitable type/size: VARCHAR(100) or equivalent text type with size 100 [1] Suitable description: student/school email address [1] Constraint: optional / not required, plus suitable format rule if given [1]

Q3: Explain why ProductCode may be stored as VARCHAR even if every code contains digits. [2]

Reveal marking points
The value is an identifier/code rather than a quantity used in arithmetic. [1] The code may contain leading zeros or non-numeric characters / its formatting must be preserved. [1]

Q4: Identify two items of metadata, other than the attribute name, that can be recorded in a data dictionary. [2]

Reveal marking points
Any two suitable examples: data type, maximum size/precision, description, required/optional status, validation rule, allowed range/values, example value. [1+1]
