Data Dictionary

A data dictionary is documentation that describes the data stored in a database. It records metadata — information about database attributes, such as their names, data types, sizes, meanings and rules.

Conceptual Anchor

The Blueprint Analogy

A building contains rooms, doors and furniture, but a blueprint describes how the building is structured. A database table contains actual records, while a data dictionary describes the structure and rules of the data stored in that table.

1 Data vs Metadata

The STUDENTS table below contains actual data:

StudentID Name BirthDate Email
S001 Ali 2009-05-12 ali@nis.edu.kz
S002 Dana 2009-11-03 dana@nis.edu.kz

A data dictionary does not mainly list Ali and Dana. Instead, it describes what StudentID, Name, BirthDate and Email mean and what values they are allowed to store.

Purpose of a Data Dictionary

Document the database structure
Gives a clear description of each attribute so developers and users understand what data should be stored.
Keep data consistent
Agreed data types, lengths and formats reduce inconsistent definitions of the same kind of data.
Support validation
Rules such as required values, allowed ranges or formats can be documented before the table is implemented.
Support maintenance and teamwork
Another developer can understand a table without guessing what each attribute was intended to represent.

What Goes in a Data Dictionary?

The exact columns used in a data dictionary can vary between organisations and database systems. A useful school-level dictionary normally records the attribute name, data type, size or format, description and important rules.

Dictionary item What it describes Example
Attribute name The name used for the column Email
Data type The kind of value that may be stored Text, Integer, Date, Boolean
Size / format Maximum length or required representation 100 characters; YYYY-MM-DD
Description The meaning and purpose of the attribute Student's school email address
Required? Whether a value must be provided Yes / No
Validation / notes Rules or restrictions applied to values Must contain @nis.edu.kz

Metadata

A data dictionary stores metadata: data that describes other data. For example, Email = Text, maximum 100 characters describes how email values should be stored.

Example: STUDENTS Data Dictionary

Attribute Data Type Size / Format Description Required? Validation / Notes
StudentID Text 4 characters Student identifier Yes Format: S followed by 3 digits
Name Text 50 characters Student full name Yes Must not be empty
BirthDate Date YYYY-MM-DD Student date of birth Yes Must be a valid date
Email Text 100 characters Student school email address No Should contain @nis.edu.kz when supplied

How to Create a Data Dictionary

1 Identify the attributes

Start from the table design or requirements. Example: StudentID, Name, BirthDate, Email.

2 Choose an appropriate data type

Decide what kind of value each attribute stores. Choose a type that matches the meaning of the data.

3 Decide size or format

Text attributes may need a maximum length. Dates may use a defined format. Numbers may need a sensible range.

4 Write a precise description

Student's school email address is useful. Email data is too vague.

5 Record important rules

State whether a value is required and record validation, allowed ranges, values or formatting constraints when they matter.

6 Review for consistency

Check that similar attributes use consistent definitions and that each dictionary row matches the intended table.

Exam technique

When asked to create a data dictionary, do not only list attribute names. Show enough metadata to describe how each attribute should be stored and interpreted.

Common Pitfalls

Writing actual records instead of metadata

A dictionary row should describe an attribute such as Email. Do not replace it with example people such as Ali or Dana.

Descriptions that repeat the attribute name

Name — “name data” is weak. Use a description that explains the meaning, for example Student full name.

Choosing a type from the current example value

If a code contains digits, that does not automatically make it an Integer. An identifier such as S001 is Text because it is a code, not a number used in arithmetic.

Forgetting constraints

A useful dictionary should record important requirements such as maximum length, required/optional status, allowed ranges or formats when these rules are known.

Exam Practice

Q1: Explain the purpose of a data dictionary. [3]

Reveal marking points
It documents metadata about the database structure. It describes attributes such as their data types, sizes/formats and meanings. It helps keep the database design consistent and supports implementation/maintenance.

Q2: A school requires the following attribute: Email — optional school email address, maximum 100 characters. Complete a suitable data-dictionary row. [4]

Reveal marking points
Attribute: Email Data type: Text Size: 100 characters Description/Rule: student school email address; optional / not required

Q3: Explain why the following is a poor dictionary entry. [3]
BirthDate | Integer | 2 | birth data

Reveal marking points
BirthDate should normally use a Date type rather than Integer. A size of 2 does not describe a complete date. The description “birth data” is vague; “Student date of birth” is clearer.

Q4: State two items of metadata, other than the attribute name, that may be included in a data dictionary. [2]

Reveal marking points
Any two suitable examples: data type, size/format, description, required/optional status, validation rule, allowed range/values.
