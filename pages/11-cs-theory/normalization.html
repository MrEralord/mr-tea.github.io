Database Normalization (1NF, 2NF, 3NF)

Normalization reorganizes database tables to reduce unnecessary duplication and prevent update, insert and delete anomalies. The key skill is recognising what an attribute depends on and decomposing the table correctly.

Conceptual Anchor

Store Facts Where They Belong

If a teacher's name is written in every student-course row, changing that teacher's name requires many updates. Normalization asks: “What fact does this attribute really depend on?” Then it stores that fact where it belongs.

Three questions to remember

1NFDoes every cell contain one atomic value?
2NFDoes every non-key attribute depend on the whole composite key?
3NFDoes any non-key attribute depend on another non-key attribute?

Why Normalize?

Repeated facts create opportunities for inconsistent data. The classic problems are called update, insert and delete anomalies.

AnomalyWhat goes wrongExample
Update anomalyThe same fact must be changed in several rowsA course name appears in 30 enrolment rows; one row is not updated
Insert anomalyA fact cannot be stored without an unrelated factA new course cannot be recorded until a student enrols
Delete anomalyDeleting one fact accidentally removes another useful factDeleting the last enrolment removes the only stored course information

Update anomaly

If the course name changes, the same fact must be updated three times. Storing the course once in a COURSE table removes that redundancy.

Functional Dependencies

A functional dependency means that one attribute, or combination of attributes, determines another.

StudentID → StudentName

Read this as: StudentID determines StudentName.

Full dependency

A non-key attribute depends on the complete composite key. Example: (StudentID, CourseID) → Grade.

Partial dependency

A non-key attribute depends on only part of a composite key. Example: StudentID → StudentName when PK = (StudentID, CourseID).

Transitive dependency

A non-key attribute depends on another non-key attribute. Example: CourseID → TeacherID → TeacherName.

1 Dependency Map

Composite PK = (StudentID, CourseID) StudentID ─────────────────────→ StudentName CourseID ──────────────────────→ CourseName │ └───────────────────────────→ TeacherID │ └────────→ TeacherName (StudentID, CourseID) ─────────→ Grade

StudentName and CourseName show partial dependencies. TeacherName creates a transitive dependency through TeacherID. Grade depends on the whole composite key.

Important modelling rule

Functional dependencies come from the business rules, not merely from the values that happen to appear in a small sample of data.

Database Normalization: First, Second & Third Normal Form

The Three Normal Forms

Normal formCore ruleQuestion to ask
1NFAtomic values; no repeating groupsDoes every cell contain one value?
2NF1NF + no partial dependency on part of a composite keyDoes every non-key attribute depend on the whole composite key?
3NF2NF + no transitive dependency between non-key attributesDoes any non-key attribute depend on another non-key attribute?

About the mnemonic

“The key, the whole key, and nothing but the key” is useful for remembering dependencies, but it is not a complete definition of 1NF. For this course, remember 1NF first as atomic values and no repeating groups.

2NF — Remove Partial Dependencies

Composite key example

ENROLMENT_RAW( StudentID, CourseID, StudentName, CourseName, Grade ) Primary Key = (StudentID, CourseID) StudentID → StudentName CourseID → CourseName (StudentID, CourseID) → Grade

StudentName depends only on StudentID and CourseName depends only on CourseID. They do not depend on the whole composite key, so they violate 2NF.

Single-column key?

If a table has a single-attribute primary key, there cannot be a dependency on only part of that key. Partial dependency is mainly a concern when composite keys are involved.

3NF — Remove Transitive Dependencies

True transitive dependency

COURSE( CourseID, CourseName, TeacherID, TeacherName ) CourseID → CourseName, TeacherID TeacherID → TeacherName Therefore: CourseID → TeacherID → TeacherName

TeacherName describes the teacher, not the course. It depends on the non-key attribute TeacherID, so it should be moved to a TEACHER table.

Full Worked Example: UNF → 1NF → 2NF → 3NF

Scenario: a student can enrol on many courses, each course has one teacher, and each enrolment stores a grade.

1 UNF — repeating course data

StudentIDStudentNameCourses
S001AliC01 / CS / T01 / Ms Lee / A; C02 / Physics / T02 / Mr Khan / B
S002DanaC01 / CS / T01 / Ms Lee / B

The Courses field contains a repeating group.

2 1NF — flatten to atomic rows

StudentIDStudentNameCourseIDCourseNameTeacherIDTeacherNameGrade
S001AliC01CST01Ms LeeA
S001AliC02PhysicsT02Mr KhanB
S002DanaC01CST01Ms LeeB

Use the composite key (StudentID, CourseID).

3 2NF — remove partial dependencies

STUDENT StudentID (PK) StudentName COURSE_TEMP CourseID (PK) CourseName TeacherID TeacherName ENROLMENT StudentID (PK, FK) CourseID (PK, FK) Grade

Student facts move to STUDENT. Course facts move to COURSE_TEMP. Grade remains in ENROLMENT because it depends on both StudentID and CourseID.

4 3NF — remove transitive dependency

COURSE_TEMP: CourseID → TeacherID → TeacherName TeacherName depends on TeacherID, so move teacher facts to TEACHER.
FINAL 3NF DESIGN STUDENT StudentID (PK) StudentName TEACHER TeacherID (PK) TeacherName COURSE CourseID (PK) CourseName TeacherID (FK) ENROLMENT StudentID (PK, FK) CourseID (PK, FK) Grade

More Short Examples

Example A — 1NF Violation

EmployeeIDNamePhoneNumbers
E01Aruzhan8701..., 8777...

Problem: PhoneNumbers contains several values in one cell. Use separate rows or a related EMPLOYEE_PHONE table.

Example B — 2NF Violation

ORDER_LINE( OrderID, ProductID, OrderDate, ProductName, Quantity ) PK = (OrderID, ProductID) OrderID → OrderDate ProductID → ProductName (OrderID, ProductID) → Quantity

OrderDate and ProductName depend on only part of the composite key. Split ORDER, PRODUCT and ORDER_LINE.

Example C — 3NF Violation

EMPLOYEE( EmployeeID, EmployeeName, DepartmentID, DepartmentName ) EmployeeID → EmployeeName, DepartmentID DepartmentID → DepartmentName

DepartmentName depends on DepartmentID, a non-key attribute. Create DEPARTMENT(DepartmentID, DepartmentName).

Example D — Already in 3NF

PRODUCT( ProductID, ProductName, UnitPrice ) ProductID → ProductName, UnitPrice

Each non-key attribute depends directly on the key, with no partial or transitive dependency.

Common Pitfalls

Calling a partial dependency “transitive”

If PK = (StudentID, CourseID) and CourseID → TeacherName, TeacherName depends on part of the key. That is a 2NF / partial dependency problem.

Splitting without explaining why

Link the decomposition to the dependency: “StudentName depends only on StudentID, so move it to STUDENT.”

Thinking every repeated value violates 1NF

The same value appearing in several rows is redundancy, but each individual cell can still be atomic.

Guessing dependencies from sample rows

Dependencies come from business rules, not accidental patterns in a small data sample.

Exam Practice

Q1: State two requirements for a table to be in first normal form. [2]

Reveal marking points
Each field/cell contains a single atomic value. [1] No repeating groups / multi-valued fields. [1]

Q2: PK = (StudentID, CourseID). StudentName depends only on StudentID. Explain why this violates 2NF. [2]

Reveal marking points
StudentName depends on only part of the composite primary key. [1] This is a partial dependency, so the non-key attribute does not depend on the whole key. [1]

Q3: COURSE contains CourseID, CourseName, TeacherID and TeacherName. CourseID → TeacherID and TeacherID → TeacherName. Explain how to put the design into 3NF. [3]

Reveal marking points
Recognise the transitive dependency CourseID → TeacherID → TeacherName. [1] Create TEACHER(TeacherID, TeacherName). [1] Keep TeacherID as a foreign key in COURSE. [1]

Q4: Explain one way normalization reduces the risk of an update anomaly. [2]

Reveal marking points
A repeated fact is stored once / in the appropriate related table. [1] The fact therefore needs to be changed in one place rather than several inconsistent copies. [1]
